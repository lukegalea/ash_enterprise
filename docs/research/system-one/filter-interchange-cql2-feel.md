# Spike S1-57 (TSET-INTERCHANGE): A published filter interchange standard for saved filters and API filters — CQL2-JSON vs DMN FEEL unary tests

**Date:** 2026-10-02 · **Status:** spike complete; recommendation inside · **Serves:** ADR 0048 (proposed), "Interchange" section; RFC S1-24 §7.4 / Q19–Q22 before freeze
**Verdict up front:** adopt **CQL2-JSON for the public API filter surface only** (Basic CQL2 + Advanced Comparison Operators profile, with a documented three-valued profile); keep the **`ash_rules` IR as the only canonical/persistence form** (as ADR 0048 already decides) and do **not** adopt FEEL unary tests as an interchange format. No bespoke filter syntax needs to be written for interchange.

## 1. The IR side, grounded (`ash_rules` source)

The IR is deliberately small. What follows is the complete inventory of expressive constructs, with semantics notes and file citations.

| # | Construct | Semantics (one line) | Source |
|---|---|---|---|
| 1 | **Triple probe** `has(subject, name, value)` | The fact `{subject, predicate, value}` must exist in working memory; `name` is always a schema-declared atom. | `lib/ash_rules/ir/predicate.ex` (moduledoc, `new/4`); `lib/ash_rules/dsl/predicates.ex` |
| 2 | **Negation probe** `neg(subject, name, value)` | The exact fact must be absent; passes when the predicate has *data with a different value*; when nothing exists, absence semantics decide (see #6). | 3 | **Strict, non-coercing equality** | `values_equal?/2` is `===` with no numeric coercion: `80` does not match `80.0` — "declare the fact type that the rule actually writes". | `lib/ash_rules/ir.ex` (moduledoc + `values_equal?/2`, lines 73–83) |
| 4 | **Conjunction only, two stages** | A rule is `applicability` (all must hold, else `:not_applicable`) then `failure_conditions` (all must hold, else `:compliant`); there is **no predicate-level disjunction** inside one rule. | `lib/ash_rules/ir/rule.ex` (moduledoc); `direct.ex` `run_rule/2`, `conjunction/4` |

| 10 | **Cardinality `:one` only** | One value per subject–predicate pair; **no arrays/collections** in 0.1. | `fact.ex` (moduledoc line 13–15; `@cardinalities [:one]`) |
| 11 | **Scope/tenancy** | Fact entries carry `tenant_scoped?`; facts are admitted, stored and filtered **per scope**, and "a filter always runs in the actor's context" — scope is ambient evaluation context, not a predicate clause. | `fact.ex` (`tenant_scoped?`); ADR 0048 "A fact is about a subject's state, at a time, in a scope"; RFC S1-24 §7.4 `scope` field |

What the IR 0.1 deliberately does **not** have: comparison/range operators, string pattern matching, array predicates, function invocation, predicate-level disjunction. Thresholds like "limit of at least X" live in *judged facts* (the judgment decides), and ADR 0048 keeps it that way — filters compose predicates; they do not re-derive them.

## 2. CQL2 (OGC)

**Status.** *Common Query Language (CQL2)*, **OGC 21-065r2, version 1.0.0, approved OGC Standard** (Interface), approval 2024-05-23, publication 2024-07-26; editors Vretanos & Portele. Spec: `docs.ogc.org/is/21-065r2/21-065r2.html`; normative JSON Schemas (draft 2019-09) and OpenAPI 3.0 schema in **Annex C**, mirrored at `schemas.opengis.net/cql2/`. It is the filter language of *OGC API — Features — Part 3: Filtering* (the `filter` parameter, §6.2 note). Two encodings are normative: CQL2-Text (§8.2) and **CQL2-JSON (§8.3, Requirement 33)**; no media type is registered (§9).

**Expressiveness inventory** (requirements classes, §2/§6/§7):

- **Basic CQL2 (§6, mandatory core):** logical `and`/`or`/`not`; comparison `=, <>, <, <=, >, >=`; `IS NULL` (`isNull`); property–literal comparisons only (Permission 1); scalar types string, number, boolean, **date, timestamp** (RFC 3339; §6.3.1).
- **Advanced Comparison Operators (§7.2):** `LIKE` (`%`, `_`, `\` escape), `BETWEEN`, `IN (list)`.
- **Case/accent-insensitive comparison (§7.3–7.4):** `CASEI()`, `ACCENTI()` functions.
- **Spatial (§7.5–7.7):** `s_intersects` (basic: points + bboxes), full DE-9IM set (`s_contains, s_crosses, s_disjoint, s_equals, s_overlaps, s_touches, s_within`), GeoJSON literals.
- **Temporal (§7.8):** intervals (`{"interval": [a, b]}`, open-ended `".."`) + 15 Allen-style functions (`t_after, t_before, t_contains, t_during, t_equals, t_intersects, …`) over instants and intervals.
- **Array functions (§7.9):** `a_contains, a_containedby, a_equals, a_overlaps`, evaluated **as sets** (Requirement 16B).
- **Property–property comparisons (§7.10), Functions (§7.11 — custom function invocation), Arithmetic (§7.12):** `+ - * / % div ^`.

**NULL / missing semantics — the three-valued fit.** CQL2 is explicitly and fully three-valued *in evaluation*:

- A predicate "evaluates to TRUE or FALSE **or the value NULL when dealing with unknown values**", with a complete Kleene truth table for `AND`/`OR` including NULL rows (§6.2, **Table 2**) — identical in shape to FEEL's Table 50.
- "The property name reference SHALL evaluate to its corresponding value, **or NULL if unset**" (§6.5, Requirement 2B) — an absent property is NULL, exactly our unassessed/stale case.
- Binary comparisons with a NULL operand **SHALL evaluate to NULL** (§6.6, Requirement 3C); `NOT` of NULL is NULL (§6.6, Requirement 4, Table 3); same rule for `LIKE` (5C), `BETWEEN` (6C), spatial (10C), temporal (14C), `CASEI`/`ACCENTI` (8D/9D), arithmetic (§7.12).
- **Result-set folding is explicit, not hidden:** "If the overall filter expression evaluates to **FALSE or NULL**, the data instance is not included in the result set" (Abstract; §6.2). So the wire format and evaluator preserve three values; the OGC result-set convention collapses NULL to excluded — the caller must query the unknown partition explicitly (`IS NULL`, or a status field), which Basic CQL2 supports natively.
- **Ambiguities, stated rather than assumed:** `IN` (Requirement 7) has **no NULL clause** — a NULL left side is not covered by the text; array predicates (Requirement 16) are defined over sets with **no NULL-propagation clause at all**. Both would need a note in any profile we publish. Also §6.3.3 (Permission 2): type casts are explicitly **system-dependent** (`'5' > 4` may error, cast either way) — no coercion contract.

**Profiles.** The standard is modular: Basic CQL2 is the minimal useful subset; every enhancement (advanced comparisons, spatial, temporal, arrays, property-property, functions, arithmetic) is a separate requirements/conformance class with its own URI (Table 1) — a product can declare exactly which classes it accepts.

**Toolchains (concrete, with maturity):**

- **`cql2` crate (Rust) — developmentseed/cql2-rs**: parse, validate (`is_valid`), convert CQL2 Text and JSON; CLI, Python bindings, WASM. Current in the 0.6.x line; production consumers include **stac-utils/rustac** (STAC API filtering) and **maplibre/martin** (tile server `cql2 = "0.6.0"` in its workspace). Mature enough to trust the encoding.
- **pygeofilter (geopython/pygeofilter, Python)**: parses CQL2 JSON and CQL2 text (CLI: `cql_json|cql2_json|cql2_text|ecql|fes|jfe`) into a common AST, with translators to SQLAlchemy, Django, Elasticsearch/OpenSearch, (Geo)Pandas, plain Python, and raw SQL WHERE. Widely used in the pygeoapi ecosystem; ~90 stars / 391 commits.
- **ldproxy / interactive-instruments and GeoServer** implement CQL2 within full OGC API — Features servers (Java; production-grade but not embeddable libraries).
- **OGC CITE** executable test suites exist for the OGC API — Features conformance classes (cite.ogc.org/teamengine).
- **Elixir: no published CQL2 package exists** (hex.pm search returns nothing; no Elixir implementation surfaced on GitHub). For the JSON encoding this is cheap: CQL2-JSON is the grammar itself — a consumer is a decoder/interpreter of a standardized JSON tree, validatable against the normative Annex C JSON Schema with any JSON-Schema validator. No text-grammar parser is required on the JSON path.

## 3. DMN FEEL unary tests

**What unary tests are.** In DMN, decision-table input entries are *unary tests*: an expression applied to a single implicit input value. Grammar (DMN 1.4, **§10.3.1.2, rules 7/13/14/15**): a positive unary test is a comparison (`>= endpoint`), an **interval** (`[a..b)`, `(a..b]` with `]`/`[` open ends), or any expression; **positive unary tests** are comma-separated (implicit disjunction); **unary tests** add `not ( … )` (negated disjunction) and `-` (anything). The simpler S-FEEL subset (§9.4, rules 5/11/12) restricts endpoints to simple values; S-FEEL decision tables are conformance level 1. Satisfaction semantics: an input entry is satisfied iff `FEEL(e in (t)) = true`; a `not(...)` entry iff it evaluates to `false`; `-` iff `e ≠ null` (**§10.2.1.1**, decision-table semantics) — note this last rule: the DMN `-` entry is literally "value present, not null", a ready-made "has any fact" test.

**Expressiveness for filter predicates.** For one field: equality, all order comparisons, intervals (half-open included), disjunction-by-comma, `not(...)`, `null` literal (`x = null`), function calls (so `matches()` for patterns), `in` over lists/ranges, `between` (a boxed convenience in DMN tables), `instance of`. For whole filters: unary tests are per-single-value — a multi-field filter is a **full FEEL expression** (`and`/`or`/`not`/`if`/quantifiers all exist in the grammar, §10.3.1.2 rules 38–47), not a unary test; or a **DMN decision table** with one input column per predicate. Both shapes run on the same evaluator.

**Three-valued logic — specified, not incidental.** "FEEL, **like SQL and PMML, uses ternary logic** for truth values" (**§10.3.2.4**); the semantics tables are **Table 50** (conjunction/disjunction: `false` dominates `and`, `true` dominates `or`, else `null`), **Table 51** (negation: `not(null) = null`, also in the built-in function table), and **Tables 52–54** (equality/inequality: `e1 != e2` is defined as `not(e1 = e2)`; null = null is true, null = anything else false; ordering comparisons with null yield null). So FEEL's three-valued semantics match our "unknown never folds" requirement *inside an expression* — but decision-table row matching requires strict `true`, so an unknown input silently fails to hit a row unless a row or column explicitly handles it (the satisfaction rule above). Unknown survives evaluation; whether it survives the *decision* depends on the table's authoring.

**What the stack already has for free.** `ash_decisions` depends on **`boxic_dmn`** (DMN 1.5 loader/validator/evaluator, pinned fork with `evaluate_with_trace` for matched-rule provenance) and **`boxic_feel` ~0.2** ("its FEEL parser and evaluator"; `ash_decisions/mix.exs` deps + comments). Verified in `deps/boxic_feel` of the fork:

- `Boxic.FEEL.evaluate_unary_test/3` is a **public API** (`boxic_feel.ex:104–119`); the AST covers `unary_test`, `unary_tests` (comma lists), `range` (interval), `in`, `not`, `between`, `instance_of`, filters, quantifiers, `if`/`for` (`boxic_feel.ex:11–32`).
- The ternary tables are implemented exactly: `feel_not(nil) → nil`; `feel_and/feel_or` false-dominates/true-dominates with `nil` otherwise (`evaluator.ex:1359–1376`); all comparisons return `nil` on a nil operand (`evaluator.ex:705–706, 855–859, 1005–1006`); `feel_equal(nil, nil) → true`, `feel_equal(nil, _) → false` (`evaluator.ex:1064–1066`).
- Conformance: **2,042 of 2,060 selected official DMN TCK FEEL cases pass** (revision `a162739…`); the 18 misses are Java external-function integration cases only (`boxic_feel` README, "Compatibility"). `boxic_dmn` targets the DMN 1.5 executable profile (FEEL namespace `…/20230324/FEEL/`, `CONFORMANCE.md`). Clause numbers above are from the DMN 1.4 document (OMG formal/23-03-01, April 2023), which was extracted directly; the unary-test and ternary-logic machinery is unchanged in 1.5, but 1.5 page-level numbering was not verified.

**Coverage check:** simple equality (1–2), range (13), conjunction (3), disjunction (4), negation over present (5), **negation over unknown/missing ×2 (6, 7, plus 14's unknown branch)**, subject-variable substitution (8), scope/tenant (9), pattern (10), array membership (11), temporal (12, 21), IR-expressible-but-neither (15, 16, 17, 18). 22 rows.

**The two findings that matter:**

1. **The languages preserve unknown in evaluation; the *result sets* fold it.** Both CQL2 (§6.2: FALSE or NULL → not in result set) and DMN row-matching (§10.2.1.1: satisfaction requires `true`) collapse unknown at the boundary — visibly and by specification, not by accident. The unknown partition is always recoverable (`IS NULL` / `status = "unknown"` / a dedicated row), but "one query, three partitions back" is not what either standard's result contract gives you. The host API must return `in` and `unknown` as separately-queried or separately-shaped results. This is a profile decision, not a format defect.
2. **Absence semantics is the one IR concept with no carrier in either candidate.** Filter #6 (`missing: :unknown`) and #7 (`missing: :false`) evaluate *differently in the IR with identical filter shapes*; CQL2 and FEEL have no way to write the difference into the document. The fix is structural: the fact schema (which bundles already carry, content-hashed) travels with or alongside any exported filter, and the interchange profile fixes judged-predicate properties to unknown-on-absence. That keeps `neg` over unknown data from ever becoming "excluded" on a peer's system.

## 5. Recommendation

**(a) Saved filters (internal persistence + wire): IR only; no standard adopted for persistence.** ADR 0048 already fixes the canonical form as the `ash_rules` IR, and the spike confirms nothing published carries the IR's load-bearing semantics: variable unification across clauses (#8), the 4-outcome lattice (#16), combining algorithms (#17), per-predicate absence semantics (#18), and strict non-coercing equality (#15). Adopting CQL2-JSON *as* the persistence format would make these either lossy or host-contract-only. Saved filters stay content-hashed bundles; a **CQL2-JSON export is worth generating as a derived view** (the bundle → CQL2 compiler is small, and every lossy row above becomes a documented export limitation rather than a storage defect).

**(b) Public API filters: adopt CQL2-JSON.** It is a real, published, modular OGC standard (21-065r2, approved 2024) with a normative JSON encoding and JSON Schema (Annex C), and — decisively — it is **the only candidate whose three-valued semantics are specified in the same terms as ours**: Kleene AND/OR (Table 2), NULL-propagating comparisons (Req 3C/5C/6C/10C/14C), unset-property-is-NULL (Req 2B), and a native `IS NULL` for the unknown partition. The mapping target is ADR 0048's derived query surface: judged predicates appear as queryable properties (tri-state field plus `status` enum `admitted_true|admitted_false|review|not_assessed|stale`), so a CQL2 filter is an ordinary filter over derived fields — indexable, policy-composed, no model in the path. Profile to declare: **Basic CQL2 + Advanced Comparison Operators** (`like/between/in`); spatial/temporal/array classes only when a surface needs them. Out-of-band contracts (documented, not encoded): scope/tenant binds at request time (#9); the unknown partition is queried explicitly (#6, #14); absence semantics fixed by profile + traveling fact schema (#18); `IN`-with-NULL and array-NULL behavior pinned locally since the spec is silent (§7.2 Req 7, §7.9 Req 16). Implementation cost: an Elixir CQL2-JSON → Ash-filter compiler (decode standardized JSON tree, validate against Annex C schema, compile to `Ash.Query` over the facts table). No text parser needed on the JSON path; no Elixir CQL2 package exists to reuse.

**DMN FEEL unary tests: use what already runs; don't make it the interchange format.** boxic_feel is paid for, TCK-proven (2042/2060), and implements the exact ternary tables we need — it remains the right engine for band tables and any per-predicate decision logic via `ash_decisions`. But as a *filter interchange* it loses: unary tests are per-single-value (whole filters need full FEEL expressions or DMN XML envelopes); the interchange unit would be a text expression or a heavyweight DMN document rather than a data format; numeric equality contradicts the IR's strict equality (Table 53, #15); and it has the same absence-semantics hole. It wins nowhere that CQL2 doesn't, and loses public adoptability (API clients would need a FEEL parser).

**Bespoke fallback cost, if neither qualified.** We would own: grammar + ABNF + JSON schema design, parser, validator, versioning, conformance corpus, and client implementations for every consumer surface (JSON:API, GraphQL, AshPhoenix forms, agent tooling) — plus the exact defect ADR 0048 forecloses: a second, private definition drifting from the derived surfaces. That is roughly a small standards body's worth of maintenance to reach a worse place than CQL2-JSON already is. The spike's conclusion is that the bespoke risk only ever materialized for the IR-internal pieces (variables, lattice, absence semantics) — and those stay in the IR canonical form regardless, so **no bespoke interchange syntax needs to be written**.

## 6. Feed-in to RFC §7.4 / Q19–Q22

- **§7.4 needs an explicit null-representation contract for interchange.** The fact table's `value` column (JSON, declared type) plus row-absence must be pinned down: **no row for (subject, predicate, scope) = unknown**; absence-as-`false` and meaningful-absence (`:no_fact`) are *per-predicate schema properties declared in the fact schema*, never inferable from a filter document. Both candidates otherwise force the #6/#7 divergence silently on a peer system. (Interacts with Q21: the one host facts table makes "absence = unknown" a physical fact — keep it that way.)
- **Freeze the derived tri-state/status enum as the interchange spelling of membership.** `admitted_true | admitted_false | review | not_assessed | stale` (ADR 0048 derived query surface) should be named normatively in §7.4 as *queryables* (CQL2's term) with declared types, so exported CQL2 filters and the FEEL band-bridge reference identical strings, and "unknown partition" has one wire spelling.
- **Scope stays out-of-band — write it down in §7.4.** Neither standard can carry scope; the contract "a filter always runs in the actor's scope" (ADR 0048) must become: filter documents are scope-free; scope binds at request time; exported filters are only valid against a schema that declares which predicates are `tenant_scoped?`/scoped. Q21's keyed-by-scope host table already supports this.
- **Q19 (admission grade per consumer): the grade constraint cannot travel in either format.** Minimum accepted `admission_grade` must be a request-time consumer parameter (or an exposed queryable property), not part of the saved filter document. §7.4 should say so before v0 freezes, so nobody later tries to encode it in the filter.
- **Q22 (standing-query events) needs no interchange work — but keep the vocabulary aligned.** `entered / left / became_unknown` maps one-to-one onto the three-valued partition and is platform-side; if standing-query *definitions* are ever exported, export them in the same format as saved filters (IR canonical, CQL2-JSON derived), and let the event payload stay native.
