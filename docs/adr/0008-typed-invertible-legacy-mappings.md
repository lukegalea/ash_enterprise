# ADR 0008 — Legacy mappings are typed expressions with proven inverses

- **Status:** accepted
- **Date:** 2026-08-17

## Context

This repository's legacy-migration story rests on
[`ash_strangler`](https://github.com/lukegalea/ash_strangler), a standalone package — **not vendored
here** — that declares how a legacy PostgreSQL relation maps onto a well-modelled Ash resource, and
derives from that one declaration a compatibility view, `INSTEAD OF` triggers, an expression index, a
resumable backfill, a drift reconciler, a `pg_notify` bridge, twelve compile-time verifiers and a
column-level lineage graph. Its thesis is *declare it once, derive the rest*.

The whole design turns on one question: **what is a transform, to the compiler?**

The obvious answer is a SQL string. A mapping says
`from: "CASE state WHEN 'active' THEN 0 ELSE 1 END"`, the generator hands it to PostgreSQL verbatim,
and the compiler checks the mapping's *shape* — is every attribute accounted for, does a joined column
claim to be writable — without ever seeing inside the string. It is the cheapest thing to build and it
fails in a specific, measurable way.

**A string has no inverse, so the inverse has to be written twice.** Writes travel back through an
`INSTEAD OF` trigger, which needs the transform run backwards. With an opaque forward direction there is
nothing to invert, so the author supplies a second string — and nothing can compare the two. Measured on
PostgreSQL 17.10, with legacy `state` ranging over `passive | pending | active | suspended | deleted`, a
forward direction sending every non-`active` value to `1` and a backward direction sending `1` to
`'suspended'`: a single `UPDATE` through the view assigning **only the email** rewrote `passive`,
`pending` and `deleted` to `suspended`. Three of five lifecycle states, no error, correct row count.
A shape check cannot catch that, because both strings are present and well-formed.

**A string cannot say which columns it reads, so lineage has to be guessed.** Drawing an edge per source
column means extracting identifiers from SQL with a regex and a keyword denylist. That works for the
expressions people usually write and fails silently otherwise — and the industrial tools that recover
column lineage by parsing SQL properly (SQLGlot, SQLMesh) document that it degrades to nothing on
`SELECT *` and unknown schemas. A diagram that omits edges it could not work out is worse than no
diagram, because a reader cannot tell "nothing feeds this" from "the generator gave up".

**A string restates what Ash and PostgreSQL already know.** The cast restates the target attribute's own
Ash type; a reconciler normaliser restates it again; a declared unique index restates something
`pg_index` can be asked about; a join predicate restates a relationship.

So one transform ends up represented six times — forward string, backward string, trigger body,
reverse-view body, guessed lineage, and the reconciler's comparison — with nothing relating any of them to
any other. The symptom that names the disease is that the mapping diagram needs **a second notation**,
four shapes and four line styles, to describe what the first notation does. Needing a second language to
talk about the first is the usual sign that the primary one is under-expressive.

## Decision

**The transform layer is `Ash.Expr` over a generated legacy twin, plus a closed grammar of invertible
combinators. Invertibility is proven at compile time or measured against real data, never asserted. Each
mapping is implemented by the weakest PostgreSQL mechanism that works.**

Four commitments, in dependency order.

**1. The legacy relation is an ordinary Ash resource — the *twin*.** Private, read-only,
`migrate? false`, generated by `mix ash_strangler.gen.twin` from `pg_attribute`, `pg_index` and
`pg_constraint`. This is what lets `expr(first_name)` resolve and therefore compile to SQL, and it is what
makes lineage a fact rather than a guess. It also removes most of the restatement: a cast is derived by
comparing the twin's column type to the target attribute's, a unique index is an `identity`, a join is a
relationship, and `mix ash_strangler.check` becomes ordinary Ash reads over the twin. A `CHECK (col IN
(…))` constraint becomes a `one_of` on the twin attribute, which is what makes the totality obligations
below decidable at compile time rather than only measurable against data.

**2. Grammar, not analysis.** Do not accept an arbitrary expression and try to invert it. Accept
combinator constructors and *emit* expressions from them, in three tiers: total bijections (a rename, a
derived cast, `zone`, `negate`, `affine`, `decode`), partial isomorphisms needing exactly one declared
datum (`coalesce`, `concat`, `collapse`), and one opaque tier — `fragment(...)`, the single node kind
meaning "not proven". Every result in reversible computing points this way: invertibility is guaranteed by
a restricted grammar, never recovered by post-hoc analysis (Janus; Theseus; Sparcl, Matsuda & Wang ICFP
2020; surveyed in Glück & Yokoyama, *TCS* 2022).

`collapse` is the case a string cannot state at all: four legacy columns and one attribute, where each
clause carries a forward guard **and** the backward assignment. Because `set:` names every legacy column
the table touches, the reverse is total and canonical by construction — there is no "which of the four do
I write" left to get wrong. It is Sparcl's `case … of { p → e with e′ }` (rule T-RCase) and HOBiT's
bidirectional `case` (ESOP 2018), with DMN supplying the hit policy and completeness vocabulary.

**3. Writability is derived, not declared.** A mapping is writable when the tool can construct and verify
its inverse. `read_only?: true` is an explicit opt-out that still requires `because:` — that text is
quoted verbatim in the runtime trigger error, which is why it is mandatory — and a `because:` without the
opt-out is refused, so the prose cannot claim a limitation the mapping does not have.

Obligations are named after the literature so an error message is searchable — `GetTotal`, `PutTotal`,
`GetPut`, `PutGet`, plus DMN completeness, masked rules, non-overlap, surjectivity, linearity, type
agreement and redundancy — and decided by **finite-domain enumeration**, not a solver. Calvanese et al.
(BPM 2016) give the reason directly: a solver *"leads to a boolean output … and cannot natively highlight
specific sets of rules that need to be added"*. `unsat` is not a next step; *"you have no clause for
`:pending`"* is. Where an obligation cannot be decided — an unbounded value space, a `fragment` that
cannot be evaluated in the BEAM — the same obligation is re-emitted as SQL and `mix ash_strangler.check`
runs it against the legacy rows.

**4. Pick the weakest PostgreSQL mechanism.** `CREATE VIEW`'s updatability rule is per **column**: a
column is updatable if it is a simple reference to an updatable column of the base relation, and otherwise
read-only, erroring only if something assigns to it. So a view may hold a mix. Measured on 17.10, a view
with two plain references and two computed columns keeps upserts, `RETURNING` and `WITH CHECK OPTION` with
no triggers at all — **those are lost to the trigger, not to the computation.** So: a simple reference
needs no mechanism; an immutable single-row derivation could be `GENERATED … STORED`; a row-local
derivation written back could be a `BEFORE` trigger on the base table plus a shadow column (pgroll's
design); and `INSTEAD OF` is for multi-table writes and genuinely non-invertible mappings.

Two limits on that last commitment, because it is the one most easily overstated. The middle two tiers are
**classified but not emitted** — both need `ALTER TABLE` against a relation the package does not own, and
a `mix` task should not do that unasked, so they fold up to `INSTEAD OF` and
`AshStrangler.Mechanism.report/1` prints the ideal tier beside the emitted one. And automatic
updatability requires exactly **one** base relation, so a join makes the whole view non-updatable however
each column classifies; the per-column rule narrows which mappings force a trigger *within* one relation.

Arbitrary SQL survives in exactly one slot, and it is loud rather than incidental:

```elixir
map :legacy_score,
  from: expr(fragment("legacy_score_udf(?)", raw_score)),
  read_only?: true,
  because: "Scoring lives in a PL/pgSQL function the finance team owns."
```

## Consequences

**Made easy.** The diagram, the reconciler's column set, the backfill, the expression index and the
trigger body are all projections of one structure, so they cannot drift. Column-level lineage is exact and
free, and constructing the structure beats recovering it — an unresolved edge is not expressible.
`mix ash_strangler.check` runs the target model's assertions against legacy rows: NULLs where
`allow_nil? false`, duplicates under a new identity grouped by the *mapping's own expression* so a
`:ci_string` attribute is checked case-insensitively even where the legacy index is not, values that will
not cast, and every obligation the compiler could not decide. Emitting OpenLineage's `columnLineage`
facet is nearly free, which matters for a tool whose job is proving to somebody that nothing was lost.

**Made hard.** Rendering `Ash.Expr` to parameter-free DDL is real work: `AshSql` parameterises every
literal and DDL cannot be parameterised, so literal escaping has to be built and confined to one audited
function — get it wrong once and it is an injection in DDL generated at compile time. `ash_postgres` has
no expression-to-DDL path to borrow (`AshPostgres.CheckConstraint` keeps `check:` as a string), though
`AshPostgres.Merge` is a shipped precedent for assembling non-Ecto SQL via `Ecto.Adapters.SQL.to_sql/4`.

The printer is written directly rather than assembled through Ecto, and the deciding reason is that **one
forward expression has to be rendered in four reference frames** — legacy columns for the view,
`alias.column` under a join, `NEW.<attribute>` inside a trigger, and bare attributes for the reverse
view. Ecto's renderer knows one, and no option changes that. The frame is therefore a parameter of the
printer, and the literal-inlining pass through `to_sql/4` is the **differential oracle** in its tests:
both renderings are executed against PostgreSQL and the results compared, which is stronger than
comparing two strings.

Expressions are stored unhydrated and hydrated only where types are needed, which puts one explicit
ordering constraint on verifiers and removes the rest.

**A trap worth recording, because it is the design's own failure mode turned inward.** Deriving a decision
from types does not inherit the *judgement* a hand-typed declaration carried. A naive legacy timestamp
feeding an aware attribute derives a `::timestamptz` cast, which reads the stored value as wall-clock time
in the **session's** `TimeZone` — measured, one value read as `12:00:00+00`, `12:00:00-04` and
`12:00:00+10:30` under three session zones. The type system can see that a cast is needed and cannot see
that one particular cast is non-deterministic, so `zone:` is required for that pair and the bare cast is
refused. Every derivation in this design needs the refusals a declaration would have carried.

**A hazard the trigger tier carries, and the guard it forces.** `WITH CHECK OPTION` on a
trigger-updatable view is not merely unenforced — it is silently absent. Measured on 17.10, the same
violating `INSERT` that a plain auto-updatable view *refuses* succeeds once an `INSTEAD OF` trigger
exists, and the row lands in the base table. So a mapping whose view carries a predicate — a tenant
filter, a soft-delete filter — must re-implement that predicate as an explicit guard inside the trigger
body, and a verifier refuses the combination otherwise. Two neighbouring facts belong with it:
`information_schema.views.is_updatable` is defined to pass `include_triggers = false`, so it reports `NO`
for a view made writable purely by triggers and `pg_relation_is_updatable(oid, true)` is what to ask;
and `INSTEAD OF UPDATE` forbids both a column list and a `WHEN` clause while `NEW` arrives fully
populated, so nothing distinguishes "absent from the `SET` clause" from "set to its current value" — a
documented choice rather than something a generator can infer.

**Foreclosed.** Arbitrary SQL in the *invertible* position. An author who wants a transform outside the
grammar must either extend the grammar or accept the opaque classification and lose the derived write
path. That is the intended trade, and it is the one thing keeping the derivation direction sound.

**What it means for the migration order here.** Mechanism tiering bears directly on
[`../plans/ash-strangler-in-reference-app.md`](../plans/ash-strangler-in-reference-app.md) §4.10, which
concludes that **authentication must cut over first** because a computed-but-writable mapping drags in an
`INSTEAD OF` trigger, which costs upserts, which breaks `ash_authentication`'s OAuth2 and OIDC register
actions — and those cannot be defined without an upsert. Per-column classification removes the premise: a
`decode`d status column does not *require* a trigger. Realising it needs a shadow column on the legacy
table, so the ordering changes once somebody adds one, and `report/1` is what says whether it is worth
doing.

**The bet being taken.** BIRDS (Tran, Kato & Hu, *PVLDB* 13(12), 2020) is the closest existing system — a
DSL compiling to PostgreSQL views plus `INSTEAD OF` triggers, verified with Z3 — and it goes the other
way: the programmer writes **`put`** and `get` is derived, because `put` determines `get` uniquely while
`get` does not determine `put`. Deriving `put` from `get` is sound here *only* because the grammar is
restricted to (semi-)isomorphisms and demands an explicit choice wherever invertibility fails. Widen the
invertible position to arbitrary expressions and this reasoning collapses, and BIRDS's choice becomes the
correct one.

### Alternatives rejected

| Option | Why not |
|---|---|
| Keep the transform as a **SQL string** | The design in Context. Cheapest to build; the inverse has to be written twice with nothing comparing them, lineage has to be guessed, and one transform ends up represented six times. |
| Accept a SQL string as **sugar**, desugaring it to `expr(fragment("…"))` so both forms coexist | Attractive, and it buys nothing. A `fragment` is by construction the node kind meaning "not proven" — it cannot be inverted, tiered to a weaker mechanism, or drawn as lineage — so a desugared mapping does not arrive in the typed layer, it arrives in that layer's worst tier and stops. Meanwhile all six representations above stay alive to serve the string form, and the printer becomes a seventh. |
| Implement **relational lenses** (PODS 2006; Links) | Their combinators are `select`, `join`, `drop` — set-of-tuples algebra with **no** value-level transforms. No cast, no concat, no `CASE`; every hard case here is value-level. Their `drop` conditions need Lossless Join Decomposition, which is NP-hard, so Links ships sound-but-incomplete approximations. Borrow the law names and the default-value discipline only. |
| **Substrait** | A cross-engine IR for exchanging relational plans between execution engines. This is one PostgreSQL schema and view/trigger DDL. |
| **PRQL** or **Malloy** as a dependency | Standalone compilers with their own toolchains; PRQL's Elixir binding is a Rustler NIF its own docs call nascent. A Rust SQL compiler invoked during macro expansion is a large liability for syntax `Ash.Expr` already provides. Take the patterns, not the code. |
| **SMT-based inverse synthesis** | Returns `sat`/`unsat`, not a localised diagnostic; Calvanese et al. reject it for exactly this reason. The guard space here is finite and small. |
| **`bff`-style bidirectionalization** (Voigtländer, POPL 2009) | Exploits relational parametricity over a *polymorphic* `get`. Monomorphic scalar column transforms have none. |
| Declare legacy columns **inline** rather than generate a twin | Self-contained, but restates the legacy schema by hand — the defect this ADR is about — and joins would still need raw SQL predicates. |
| Guess lineage from SQL with a **better parser** | A better regex is still a guess, and parsing properly means shipping a SQL parser — which the tools that do document as degrading to nothing on unknown schemas. |
| Report a failed round-trip as a **warning** | A warning in a build log is not a refusal, and the corruption in Context is exactly what survives one. |

## Reversal

Cheap, because the package is 0.x and this repository does not depend on it yet.

**To abandon the typed layer entirely:** the string form is not retained anywhere, so reverting means
reintroducing it and hand-translating every mapping into `from:`/`to:` strings. The round-trip proofs go
with it. That cost is deliberate — a retained compatibility path is a second design to maintain and keeps
alive the shape this ADR rejects.

**To abandon the twin but keep typed expressions:** replace `source <Twin>` with a `columns do … end`
block inside `source`, restating each legacy column and its type by hand. Everything downstream — lineage,
the printer, the obligations — is unaffected, because it only needs types to exist, not to have been
introspected. Costs the derived cast, the relationship form of a join, and the `pg_index`-checked
identity.

**To abandon mechanism tiering:** replace the per-column classification with a single rule that any
computed writable mapping forces `INSTEAD OF` triggers. One function, and §4.10 of the reference-app
plan's ordering conclusion holds again.

**To reverse the derivation direction** (BIRDS's choice: write `put`, derive `get`): the expensive one,
because it inverts the DSL's surface. Budget a rewrite of the entities, the printer's call sites and every
fixture. The signal that it is necessary would be sustained pressure to accept arbitrary expressions in
the invertible position — at which point the grammar guarantees nothing and `put` should be the thing
declared.

## What this repository does about it

Nothing yet, and deliberately. There is no `ash_strangler` dependency here, and the demo remains
**DEFERRED** behind Organization/tenancy and hierarchy security — see
[`../plans/ash-strangler-in-reference-app.md`](../plans/ash-strangler-in-reference-app.md). This ADR
records the design so that the plan and the eventual adoption are arguing from the same premises.

When the demo is built, the dependency line is `{:ash_strangler, path: "../ash_strangler"}` plus
`:ash_strangler` in `.formatter.exs`'s `import_deps`. Clarity is already mounted here, so the package's
`Clarity.Content` provider lights up with no wiring.

The deep design argument — the combinator grammar, the ten obligations with their citations, the
PostgreSQL measurements behind mechanism tiering, and the reference-frame problem the printer solves —
lives in `documentation/topics/the-transform-layer.md` in the `ash_strangler` repository. It is not
vendored here, so that is a name rather than a link.
